# GitHub Tooling

## Goal

Build CLI and MCP tools that let agents (and contributors) read and act on the Open Austin GitHub org — issues, project boards, labels, milestones — with the same fluency that personal automation tools provide for personal work.

The tooling should make the org's work visible and actionable without requiring constant API queries, and should give any contributor who clones the repo a consistent environment for working on org tasks.

---

## Non-Goals

- This is not a replacement for GitHub's UI. It's an agent-facing layer on top of it.
- We are not building a private vault. Snapshots are gitignored working files, not a separate tracked database. The repo itself is the source of truth for tooling and docs.
- We are not automating board decisions or governance processes. That work is highly human and interpersonal.
- Google Drive integration is a future consideration, not part of this spike. (Note: giving agents Google Drive access would allow reading shared docs, wiki exports, meeting notes etc. — worth revisiting once the GitHub layer is stable.)

---

## Why Snapshots?

Three reasons snapshots are better than direct API queries:

1. **Context loading** — An agent loads `snapshot/issues.md` (~50KB of markdown) once at session start and has full issue context in working memory. During analysis and triage, the agent reasons over local data without hitting APIs mid-session. Same as the personal tooling loading `sources/trello.md` — full board visibility without per-card queries.

2. **Consistent view during work** — Triage sessions can take time. If the state changes mid-session (someone closes an issue, adds a label), you want to work from "the state when I started" rather than have your analysis invalidated partway through. The snapshot gives you a stable working copy. Re-sync when you're ready for fresh state.

3. **API efficiency** — Analyzing 27 issues + 2 boards + labels + milestones one-at-a-time would be 30+ API calls. A sync command batches everything into ~5 calls. GitHub's rate limit (5000 req/hr) isn't tight, but batching is cleaner and faster.

## Mental Model

This is a direct port of that methodology to a shared org context:

```
gh / GraphQL API
      ↓
  sync command (batched reads)
      ↓
 snapshot/ (gitignored)
  issues.md            ← grouped by team, bounded, with staleness
  board-org-kanban.md  ← current board state
  board-open-roles.md
  labels.md
      ↓
  agent loads snapshot into context
  agent analyzes / drafts changes
  agent proposes → user approves
      ↓
  write commands (guarded, dry-run)
      ↓
  re-sync (get fresh state)
```

The snapshot is **read-only context, not a write-back database**. Agents read it to understand state. Changes go through explicit write commands, then re-sync.

## Repo Layout (intended)

```
tools/
  sync/
    issues.sh        # fetch issues → snapshot/issues.md
    boards.sh        # fetch board state → snapshot/board-*.md
    labels.sh        # fetch label taxonomy → snapshot/labels.md
    run.sh           # run all sync commands
  write/
    label.sh         # add/remove labels (dry-run required)
    move.sh          # move board item between columns (dry-run required)
    close.sh         # close issue (dry-run required)
    comment.sh       # post comment (dry-run required)
snapshot/            # gitignored — generated by sync tools
  issues.md
  board-org-kanban.md
  board-open-roles.md
  labels.md
```

All write tools take `--dry-run` as a flag and print a before/after plan without executing. No write runs without explicit user approval of the plan.

**What other tools might we need?**
- Most GitHub writes can happen via `gh` commands directly (`gh issue edit`, `gh issue close`, etc.) or the MCP server if configured
- The sync tool is the foundation that everything else depends on
- Write tools listed above are guarded wrappers around common operations to enforce dry-run discipline
- For now, focus is on sync + label management — other write tools can be added as needed

## Snapshot Design

The snapshot trades completeness for signal density. It is not a raw JSON dump — it is bounded, rendered Markdown that an agent can load as context without hitting the API.

Each snapshot file should include:
- Generated timestamp
- Total count + brief staleness summary
- Issues grouped by label/team, with: number, title, assignees, last-updated age, status
- Truncated body (first 200 chars) — enough for triage, not a full dump

The snapshot directory is gitignored. Agents run `sync` at the start of a session to get fresh state.

## API Surface

- **Issues, labels, milestones, assignees:** GitHub REST API via `gh issue ...`
- **Projects v2 (board columns, Status field, custom fields):** GitHub GraphQL API via `gh api graphql` and `gh project ...`
- Moving a card between columns = updating the `Status` single-select field on a project item via GraphQL, using opaque node IDs from `gh project field-list`
- Auth: `GH_TOKEN` fine-grained PAT with `repo` + `project` (read/write) org permissions. See `.env.example`.

## MCP Layer

The GitHub MCP server (`github/github-mcp-server`) is an optional interactive desktop-app layer. It would be configured in your MCP settings (if using Claude Desktop or similar) and would expose GitHub operations as tools agents can call directly.

**Current state:** Not yet configured. We're using `gh` CLI directly, which is working fine.

**When MCP becomes useful:**
- Interactive "look at the board and help me triage" sessions in Claude Desktop
- Natural language GitHub operations without writing shell commands
- Real-time exploration during a conversation

**The relationship:**
- The CLI tools are the durable, scriptable path — deterministic, auditable, runnable without a desktop app
- The MCP server is a convenience layer on top of the same underlying GitHub API
- They are not mutually exclusive — CLI is authoritative for repeatable behavior, MCP is for interactive sessions

For now, building the CLI sync and write tools is the priority. MCP configuration can happen later if it proves useful.

## Write Safety

These rules are non-negotiable and apply to all write tools. See `AGENTS.md` for the full list.

- `--dry-run` is required on all write commands
- Re-fetch state before any mutation — never act on a stale snapshot
- No bulk writes without a reviewed plan
- No hard deletes — prefer close/archive/relabel
- Comments notify real people — always confirm before posting

---

## Open Questions

- Shell scripts vs. a lightweight Python CLI? Shell is simpler and closer to that pattern. Python gives better argument parsing and testability. Decide before building write tools.
- Should the sync command produce separate files per board, or one unified snapshot? Probably per-board for now, unified index later.
- Rate limits: GitHub REST is 5000 req/hr for authenticated users; GraphQL counts differently. Snapshots should batch efficiently and avoid polling.
